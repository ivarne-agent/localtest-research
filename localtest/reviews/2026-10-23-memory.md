## How `free` counts on this machine

procps-ng 4.0.4 computes `used = MemTotal - MemAvailable` (checked: 7949 - 6139 = 1810 for A against `free`'s 1809).
Older `free` used `MemTotal - MemFree - Buffers - Cached - SReclaimable`; the script prints both. The difference is
`Shmem`: it lives in `Cached` (so in `buff/cache` and `shared`) but cannot be reclaimed without swap, so `MemAvailable`
leaves it out and the new `used` contains it. On this stack `Shmem` is large, for two reasons:

- **.NET's W^X double mapping.** Since .NET 7 the JIT writes code through one mapping and runs it through another of
  the same `memfd:doublemapper` (shared memory). Every JIT-ing .NET process carries 17 to 99 MiB of `RssShmem`
  (the containers' `shmem` column); the native AOT front door and the non-.NET containers carry none. Checked on a
  live .NET 10 process: 64 `memfd:doublemapper` mappings.
- **tmpfs and Postgres.** Postgres's shared buffers are shared memory (50 to 83 MiB under the full stacks); in minimal
  mode its data directory is a tmpfs too, and the Postgres cgroup holds 175 MiB of `shmem`.

`available` is `MemFree` plus the page cache and reclaimable slab the kernel can drop (each less a low-watermark
reserve, here 33 MiB). The image layers the containers read (the .NET runtime, the services' DLLs, Postgres) are page
cache: they count in `buff/cache` and in `available`, not in `used`, unless they are tmpfs or shared memory.

## Reconciliation

reclaimed (`SUnreclaim + KernelStack + PageTables + Percpu`) and a remainder; the containers' part comes from their

- **The remainder** (120 to 190 MiB in every row, the baseline included) is what `MemAvailable` holds back besides
  those: the low watermark (33 MiB) subtracted from free memory, page cache and reclaimable slab each, and kernel
  allocations outside the four fields. I cannot confirm its split further; it does not grow with the stack.
- **Containers** (F): anon 902 + shmem 709 + kernel 88 = 1699 of the 3802; with the cgroups' page cache (228) that is
  the 1927 of `memory.current`. Their page cache is not in `used`.
- **Host** (F): anon 1380 and shmem 473 against the baseline's 577 and 136: about 1.1 GiB more, which is the stack's
  host processes (PSS 1143) and the build server (403) less their file-backed part, which is cache.
- **The page cache on `libpod_parent` itself**: 0.8 to 1.1 GiB of file pages charged to the Podman cgroup root while no
  container runs (877 at the baseline, 924 at the end). These are image-layer and volume pages read by containers that
  have since been removed; the kernel moves a removed cgroup's charges to its parent. They are in `buff/cache` and
  `available`, nowhere in `podman stats`, and not in `used`.
- **Image layers**: the 18 images of F are 4.1 GB on disk; only the pages the processes touch are read, and they are
  cache. `RssFile` (75 to 139 MiB per .NET container) is such cache mapped into the process, which is why `VmRSS`
  overstates a .NET container (sum of `VmRSS` 2667 against `memory.current` 1927 in F) and the cgroup's `file` is
  smaller: a page is charged once, to the first cgroup that read it.
- **Postgres is the opposite case**: its main process has 36 MiB of RSS, its cgroup 193 to 352, because each client
  connection is a backend process and the shared buffers are shared memory.

## Why 18 .NET containers fit in about 4 GB

Every .NET service runs Server GC, and nothing limits it: each image's `*.runtimeconfig.json` has
`"System.GC.Server": true` (the default of `Microsoft.NET.Sdk.Web`, kept by every component and by the native AOT front
door, whose processes each run four `.NET Server GC` threads, one per core), and no manifest `envs`, Dockerfile `ENV` or
process environment sets `DOTNET_gcServer`, `DOTNET_GCHeapHardLimit` or another GC knob (the only `DOTNET_` setting
besides the image's version variables is `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT` in eight images; [`memory/F-gc.txt`](memory/F-gc.txt)).
No container has a memory limit (`podman stats` shows the host's 8.3 GB as the limit), so the GC sizes itself against
the whole machine. What keeps the heaps small is the runtime: the containers run .NET 10 (10.0.10 to 10.0.13), where
Server GC uses dynamic adaptation to application sizes (the default since .NET 9), which starts with one heap
and grows the heap count and the gen0 budget with the live data (the documented behaviour; the heap count was not
measured here). An idle service with a few hundred cached rows needs
little: 15 to 60 MiB of anonymous memory (Access Management and Dialogporten's WebApi, the largest, 83 to 170). The
host apps target net8.0 and run on the 8.0.32 runtime, where dynamic adaptation is off by default and Server GC keeps one heap per
core, and still sit at 41 to 48 MiB of anon when idle; under load all of these grow, the smoke suite moved Storage from
84 to 280 MiB.

The rest of a .NET process is code. The JIT's output is in the `memfd:doublemapper` shared memory (17 to 99 MiB per
process): that, not the heap, is often the largest private part, and it shows as `shared` and `buff/cache` in `free`.
The runtime and the service's DLLs are page cache, read once per image layer and reclaimable. Native AOT is used only
by the front door (`localtest`, `PublishAot`), which runs in 13 to 18 MiB of anon and 30 to 38 MiB of RSS, with no JIT
and so no double mapping; `pdf3` (`/app/main`, no .NET threads) and Redis are similarly small. Shared base layers help
less than assumed: the 14 .NET containers map ten distinct copies of `libcoreclr.so` (by inode), from four runtime
patch versions on Alpine 3.23, Alpine 3.24, Ubuntu 24.04 and Ubuntu 26.04 bases; only Events, Notifications and
Profile, the three Dialogporten hosts, and the workflow engine with the adapter share one. Since that sharing only saves
page cache, it hardly changes `used`. So 14 .NET services at 50 to 250 MiB each, Postgres at 200 to 350 and the small
ones make 1.9 GiB of container memory, of which 1.7 GiB is in `used` (the rest is their page cache). The full sample's
3.8 GiB `used` is those 1.7 GiB, about 1.1 GiB of anonymous and shared memory of the Aspire host processes and the
build server, and the 0.9 GiB the machine uses with nothing running.

## What surprised me

- `free`'s `used` already includes `Shmem` (procps-ng 4.0.4 computes it from `MemAvailable`), so the .NET double
  mapping and the tmpfs count as used even though `free` lists them under `buff/cache`.
- About 0.9 GiB of page cache stays charged to `libpod_parent` with no container running, invisible to `podman stats`.
- Under Aspire the host side is bigger than the platform in minimal mode: 1.2 GiB of PSS (AppHost 0.3, DCP 0.3 in
  eleven processes, dashboard 0.14, launchers 0.14, apps 0.23) against 0.43 GiB for the four containers, plus a 0.4 GiB
  Roslyn build server left by `dotnet run`. The build server also follows `studioctl run` (0.24 GiB) and lingers after
  the app stops; it was killed by PID after each run here.
- Storage roughly triples (84 to 280-296 MiB) once an app registers or the smoke suite runs; nothing else grows as much.
- In minimal mode Postgres's tmpfs is the largest item (175 MiB of the 424).
- The full stack's containers had more memory after the AppHost stopped than while it ran (above).
